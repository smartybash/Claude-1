## 4. Frozen RP-011 block-relative specification

Verified on **counts and distributions only**. The verifying script,
`scripts/orderflow/rp011_spec.py`, asserts at load that the frame it opened
contains **no outcome column**; it cannot read one.

### 4.1 Why the threshold changes

| block | windows/session | median imbalance | block's own p90 | median volume | cleared the pooled p90 |
|---|---|---|---|---|---|
| opening | 50 | 0.0755 | 0.1678 | 1,038 | **3.5%** |
| morning | 180 | 0.0861 | 0.2091 | 626 | 7.2% |
| midday | 300 | 0.1091 | 0.2605 | 299 | 15.1% |
| closing | 230 | 0.1126 | 0.2670 | 270 | **16.5%** |

Opening windows carry 3.5× the midday volume and are the **least** one-sided, so
the opening block's own p90 sits below the pooled gate of 0.2496. A pooled
threshold partly encodes **time of day** — the exact axis RP-011 stratifies on.
Justified by sampling design, not performance. This creates RP-011 as a new
specification and does not reopen RP-010.

### 4.2 The frozen construction

| element | value |
|---|---|
| windows | 30 s, non-overlapping, cash only, first/last 5 min excluded |
| blocks | opening 09:35–10:00 · morning 10:00–11:30 · midday 11:30–14:00 · closing 14:00–15:55 (ET) |
| **thresholds** | **block-specific** percentiles over the **prior ten completed sessions** |
| aggression | block p90 imbalance |
| high impact | block p80 ticks/1k |
| low impact | block p20 ticks/1k |
| INITIATIVE | aggression ≥ p90 **and** impact ≥ p80, aligned |
| ABSORPTION | aggression ≥ p90 **and** impact ≤ p20 |
| cooldown | 5 minutes from any retained event |
| cap | **two** events per state per block — 8 + 8 = 16 per session |
| **separation** | **the two events of a cell must be ≥ ⅓ of the block's length apart** |
| sides | symmetric buy and sell |

Resulting block-specific thresholds (median over sessions):

| block | p90 imbalance | p80 ticks/1k | p20 ticks/1k |
|---|---|---|---|
| opening | 0.1767 | 120.5 | 46.6 |
| morning | 0.2117 | 126.8 | 46.1 |
| midday | 0.2625 | 152.4 | 46.5 |
| closing | 0.2646 | 146.7 | 44.1 |

### 4.3 The separation rule — a revision made before collection, as instructed

The first count check on the specification as briefed (block-relative
thresholds, cap 2, chronological retention) **failed condition 5**: the cap bound
on **84.0%** of midday absorption sessions, 68% of midday initiative, 56% of
morning absorption. That is RP-010's first-come defect in a milder form, inside
the cell instead of inside the session.

Two repairs were measured on counts only:

| rule | events/session | max cap-bind | max block share |
|---|---|---|---|
| cap 2, chronological (as briefed) | 11.60 | **84.0%** | 31.7% |
| cap 3 | 14.76 | 72.0% | 35.0% |
| cap 4 | 17.04 | 56.0% | 36.9% |
| cap 5 | 18.76 | 28.0% | 38.0% |
| **cap 2 + ⅓-block separation** | **10.52** | **28.0%** | **31.9%** |

Raising the cap to 5 satisfies the condition but triples the theoretical maximum
to 40 events/session and pushes the block share to 38.0%, against a 40% ceiling.
**The separation rule achieves the same binding rate while keeping the two-event
cap you froze**, and it is **causal** — decidable at the moment of the event — so
it survives into a live rule, which a look-back selection would not.

Three separation values were tried **on counts only**: ⅓ binds on 28%, 0.45 on
4%, 0.50 on 0%. All three pass. **⅓ is chosen as the smallest that passes**,
discarding the fewest candidates. No outcome informed the choice and none could.

## 5. Forward-recording quality gate

A new RP-011 data ledger begins at the **first genuinely new recorded session**.
Each session must pass every mandatory check **before** any outcome is computed;
a session failing one is excluded at the loader.

| # | requirement | how it is verified | mandatory |
|---|---|---|---|
| 1 | measured 0.25-point tape grid | `dataquality.min_increment` on actual prices — never the filename | **yes** |
| 2 | full cash-session coverage | `tape.is_full_session` | **yes** |
| 3 | aggressor labels, zero nulls | label set and null count per session | **yes** |
| 4 | valid status file | `_status_YYYYMMDD.txt` present and parseable | **yes** |
| 5 | monotonic microsecond timestamps | `dataquality.monotonic` + unit assertion (ledger §9) | **yes** |
| 6 | no duplicate-date ambiguity | `dataquality.duplicate_dates`; selection by measured quality, never by extension | **yes** |
| 7 | no prior research use | not in the 44-date RP-010 list; `holdout.is_sealed` false | **yes** |
| 8 | usable cumulative fills | `CUM_` file present and parseable | diagnostic |
| 9 | usable BBO | `BBO_` present, measured 0.25 | diagnostic |
| 10 | usable depth where available | `L2_` present | diagnostic |

Checks 8–10 are **diagnostics**: RP-011's primary construction reads the tape
only, so a session missing depth is usable and is recorded as such rather than
discarded. Checks 1–7 are exclusions.

The ledger records, per session, every measured value — not a pass/fail flag —
so that a later change of threshold can be re-derived without re-reading tape.

**Counts gate — all must hold on fresh data before any forward outcome:**

1. no empty state × time-block cell
2. no time block contributing more than 40% of retained events
3. buy and sell events in every interpretable cell
4. cap binding on no more than 50% of sessions within any cell
5. at least three time blocks with both states in ≥ 30 independent sessions
6. genuine closing-period representation
7. no cell dominated by fewer than five sessions

**If the counts gate fails, RP-011 returns for redesign.** The thresholds and the
separation rule are not amended using outcome data.
